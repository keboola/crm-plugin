# Weekly changelog — local preview and tuning

The weekly changelog is generated by
[`scripts/weekly_changelog.py`](../../../../scripts/weekly_changelog.py) and
published by
[`.github/workflows/weekly-changelog.yml`](../../../../.github/workflows/weekly-changelog.yml)
on its Sunday cron (`0 13 * * 0`, ~15:00 CEST). The scheduled run **publishes
directly**: it commits `docs/changelog/<date>.md` to `main` as the release bot,
which triggers `changelog-publish.yml` (cursor tag → GitHub Release → Slack).

There is **no `changelog` label**. The generator receives every PR merged in
the window and the model selects the user-facing ones by following
[`docs/changelog/INSTRUCTIONS.md`](../../../../docs/changelog/INSTRUCTIONS.md).
That file is the prompt: it is sent verbatim in both model calls, so tuning the
changelog means editing it — not editing the script.

## 1. Dry-run a window

```bash
export ANTHROPIC_API_KEY=...            # any key with Messages API access
GH_TOKEN=$(gh auth token) \
  python3 scripts/weekly_changelog.py --dry-run --from-ref v0.83.1
```

- `--from-ref <tag>` sets the window start (exclusive). Without it the window
  starts at the newest `changelog-YYYY-MM-DD` tag, or bootstraps to the last 7
  days on a first run.
- `--to-ref <ref>` sets the end (default `HEAD`). Both bounds are enforced, so
  rehearsing an old window does not sweep in everything merged since.
- `--today YYYY-MM-DD` fixes the entry date — useful to reproduce a specific
  Sunday's output.
- `--dry-run` writes nothing, commits nothing, pushes nothing. It prints the
  decisions table, the full rendered `docs/changelog/<date>.md`, and the Slack
  bullets.

Requires the repo checked out with tags (`git fetch --tags`) and `gh` logged
in — the PR list comes from `gh pr list`, the window bounds from local git.

## 2. Read the decisions table

The first thing printed is one row per merged PR:

```
| PR | Title | Verdict | Reason |
| #1541 | fix: Generate Order Form auth bypass | include | Reps got "Invalid or expired token" |
| #1573 | ci: deploy alerts | exclude | Deploy resilience, nothing a user meets |

**12 included / 54 merged PRs in the window.**
```

Read it as a diff against your own judgement:

- **A user-facing PR marked `exclude`** — usually its body did not say what a
  user sees. Two fixes, and the first is better: write PR bodies that name the
  symptom and the audience. Otherwise add or sharpen a rule in
  `INSTRUCTIONS.md` ("What counts as user-facing", or the path table).
- **An internal PR marked `include`** — add it to "What does not count", or add
  the path to the path-heuristics table.
- **Two PRs on the same change written as two items** — they needed the same
  `theme`; the "One theme, one item" rule is what governs that.
- **A wrong or overclaiming sentence** — the Style and "Never promise anything
  the body does not support" rules; tighten them and re-run.

In CI the same table lands in the job's step summary, so a published week can
always be audited without re-running the model. It is deliberately never
committed.

## 3. Iterate on the instructions

`docs/changelog/INSTRUCTIONS.md` is plain Markdown and reviewed like code.
Edit it, re-run the same dry run, and compare. Keep the "Output contract"
section intact — the script parses JSON from both calls, and the frontmatter
around the body is rendered deterministically in code, not by the model.

Two rules are also enforced in code, so loosening them in the prose alone
achieves nothing: **24 items / 12 Slack bullets** (anything over is truncated)
and **no PR references or links anywhere** (`(#1234)`, `#1234` and markdown
links are stripped from the body and the bullets before rendering). The reader
has no repository access.

## 4. Fix or regenerate a published week

The entry is a normal file on `main`, so a typo is a one-line PR against
`docs/changelog/<date>.md` — the in-app `/releases` page renders straight from
`main`, and `changelog-publish.yml` does not re-tag, re-release or re-announce
an entry whose tag already exists.

To have the model rewrite a whole week:

```bash
gh workflow run "Weekly Changelog" \
  -f from_ref=changelog-2026-09-07 -f to_ref=<the week's HEAD> \
  -f dry_run=false -f force_tag=true
```

`force_tag` overwrites the existing entry file. The already-published tag,
Release and Slack post stay as they are — Slack does not announce the same week
twice — so a rewrite reaches readers through `/releases` and the file, not
through a second announcement.

To rehearse the same thing first, run it with `dry_run=true` (the dispatch
default) and read the step summary.

## 5. Empty weeks and failures

- **Nothing user-facing selected** → no file, no commit, no entry. The run
  exits 0 and the decisions table says why.
- **The model reply could not be parsed** → nothing is selected and nothing is
  published, deliberately: a title-only or invented changelog reaching every
  CRM user is worse than a missing week plus a red-ish log. Re-run with
  `--dry-run` to see the reply.
- **`ANTHROPIC_API_KEY` missing** → exits 1 before any model call.
